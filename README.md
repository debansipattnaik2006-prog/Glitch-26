# GLITCH’26 — ITM Welcome Ceremony Platform

A responsive React/Vite event website with student pass registration, QR tickets, single-use server-side entry verification, and a separate authenticated admin dashboard.

## Included
- Galaxy-themed public website: animated intro, countdown, about, event details, directions, timeline, guidelines, dress code and contacts.
- Student registration backed by PostgreSQL, server-side validation and unique roll-number constraint.
- Personalized QR entry pass. The QR contains only the unique pass UUID, not student personal details.
- PDF/PNG export and print support.
- Admin login, overview cards, searchable/filterable registration table, CSV export, year-wise chart, camera QR scanner and manual pass-ID verification.
- Atomic single-use verification: PostgreSQL row locking prevents two scanners from approving the same pass concurrently.

## Requirements
- Node.js 20 or newer
- PostgreSQL 14+ (a hosted PostgreSQL database such as Supabase works)
- npm

## 1. Database setup
Create a PostgreSQL database. Run `server/sql/schema.sql` in its SQL editor or with `psql` against that database. The schema creates `admins` and `registrations`, including a unique constraint on normalized roll numbers and unique pass IDs.

## 2. Configure the server
```bash
cd server
cp .env.example .env
```
Edit `server/.env`:
- `DATABASE_URL`: PostgreSQL connection string. For hosted databases, use the provider's connection string and SSL.
- `JWT_SECRET`: replace with a long random secret (32+ characters).
- `ADMIN_EMAIL` and `ADMIN_PASSWORD`: the first admin account is inserted on server startup if that email does not already exist. Use a strong unique password. The password is hashed with bcrypt; it is never sent to the frontend.
- `CLIENT_ORIGIN`: frontend origin. For production, set this to your deployed frontend origin (or comma-separated allowed origins).

The server does not overwrite an existing admin password on restart. To rotate it, update `password_hash` with a bcrypt hash generated by a trusted one-time admin script, or create a new admin using your own controlled provisioning process. Do not commit `.env`.

## 3. Configure event details
Edit `server/src/config.js`. This is the central event configuration for the public website: date/time, optional confirmed end time, venue, map URL, timeline and coordinator contacts. Leave `eventEnd` blank until organizers confirm the end time; the live-event state will continue until an end time is configured. The default map link is a Google Maps search link using the supplied venue wording; confirm the exact building pin with the college before publishing. No coordinates have been guessed.

## 4. Install and run locally
From the project root:
```bash
npm install
npm install --prefix server
npm install --prefix client
npm run dev
```
- Frontend: http://localhost:5173
- API: http://localhost:4000/api/health

Optional frontend API override: create `client/.env` with `VITE_API_URL=http://localhost:4000/api`.

## 5. Production deployment
1. Deploy the `server` directory to a Node hosting provider. Set all server environment variables there. Run `npm start`.
2. Deploy the `client` directory as a static Vite site. Set `VITE_API_URL=https://YOUR-API-HOST/api` at build time, then run `npm run build`.
3. Set `CLIENT_ORIGIN` on the API to the exact frontend origin. Use HTTPS for both.
4. Run the SQL schema against the production database before opening registration.
5. Create the admin credentials securely and change/remove the bootstrap `ADMIN_PASSWORD` environment variable after the initial admin has been provisioned.
6. Test a real registration, duplicate roll number rejection, PDF/PNG output, camera permissions, invalid QR, valid QR and second scan (which must show already used).

## QR verification and security notes
- A generated QR code is an identifier, not proof of entry approval. The admin scanner calls the authenticated backend to check the pass.
- The backend changes `PENDING` to `USED` inside a transaction while locking the registration row. A second concurrent scan cannot approve it again.
- Admin routes require an eight-hour signed JWT. Login attempts and general API requests are rate limited. Helmet headers, CORS, Zod validation, parameterized SQL and bcrypt password hashing are enabled.
- Do not put database credentials, JWT secrets or admin passwords in `client/` or any `VITE_` variable.
- Add HTTPS, database backups, monitoring and a documented admin credential recovery process before public production use. Consider adding CSRF protections if cookie-based authentication is introduced later.
- The admin dashboard intentionally displays student contact numbers nowhere. The registration table exposes only the fields required for entry operations.

## Notes / editable placeholders
Coordinator names, phone and email are intentionally set to “To be announced”. Replace them in `server/src/config.js` only after the organizers confirm the details. Confirm the venue's exact map pin and final schedule before publishing. Schedule times are editable placeholders and should be approved by event coordinators.
